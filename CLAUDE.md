# gameWE web - notes for Claude

Next.js (App Router, standalone output) stats website for the gameWE
collector's HLstatsX/gameME database (MariaDB/MySQL or PostgreSQL). Public
pages under `src/app/[game]`, forum signatures under `src/app/sig`, admin
area under `src/app/admin` (session cookie signed with `ADMIN_SECRET`,
optional TOTP, `src/lib/auth.ts`, `src/lib/totp.ts`). Runs behind nginx
under a base path (`BASE_PATH`, e.g. `/new`), access log via
`scripts/access-log.cjs`. Config: `.env.example` → `/etc/gamewe/web/web.env`.

Build and check: `npm ci`, `npm run lint` (tsc), `npm run build`,
`make package`.

Version in `VERSION`, `package.json` and `package-lock.json`; history in
`CHANGELOG.md`. Third-party licenses: `THIRD-PARTY-LICENSES.md` and the
`/licenses` page.

Releases: Conventional Commits + semantic-release (`.releaserc.json`). CI
(`.github/workflows/build.yml`) builds and checks every push to `main` and
publishes the image `ghcr.io/dennispohlmann/gamewe-web:edge`;
`feat`/`fix`/breaking commits make semantic-release bump the version files,
write `CHANGELOG.md`, commit `chore(release): vX.Y.Z [skip ci]`, tag
`vX.Y.Z` and publish the GitHub release with the tar.gz (+ `.sha256`) and
the image tags `<version>`, `<major>.<minor>`, `latest`. There is no
tag-triggered workflow.

## Documentation layout (the same in all gameWE repos)

- Root: `README.md` (overview, requirements, quick start, documentation
  table, components, building, license), `CHANGELOG.md` (generated),
  `LICENSE`, `THIRD-PARTY-LICENSES.md`, `CLAUDE.md`.
- `docs/`: `INSTALLATION.md` (install, update, uninstall, troubleshooting),
  `CONFIG.md` (all settings), `USAGE.md` (commands, pages, operation),
  `INTERFACE.md` (log lines, RCON commands, APIs between the components),
  `DEVELOPMENT.md` (build, tests, CI, releases); repo-specific extras:
  `screenshots/`.
- New documentation goes into the matching file there; no other top-level
  doc files and no per-distribution install guides.

## Security is part of every change (mandatory)

1. **Every change:** before you call a change done, commit it or open a PR,
   run the `security-check` skill on the diff and fix what it finds. Say in
   your answer which checklist points the change touched and the result
   (one or two lines are enough when nothing was found).
2. **Every release, without exception (standing rule from Dennis):**
   releases are made by semantic-release in CI when `feat`, `fix` or
   breaking-change commits reach `main` (version bump, `CHANGELOG.md`, tag
   `vX.Y.Z`, GitHub release). Before pushing such commits to `main`, run
   the `release-security-gate` skill over the whole repo, without asking
   first. Never tag by hand or edit version files / `CHANGELOG.md`; report
   the gate result and ask Dennis for the go before the push.
3. **Sensitive data, every task (standing rule from Dennis):** before you
   call a task done, commit or publish anything, run the
   `security-privacy-audit` skill (credentials, personal data, IPs and
   hostnames, Steam IDs and other account identifiers, private files) over
   the working tree, the diff, docs and the commit message, and end the
   answer with its audit summary. A `BLOCKED` finding stops the commit;
   report only category and location, never the value.
4. A finding you cannot fix in scope goes into the answer with file:line,
   impact and a proposed fix. Never silence a check or weaken a validation
   to get green.

## Before every commit (mandatory, standing rule from Dennis)

Run the `pre-commit-checklist` skill before every `git commit`, together
with `security-check` and `security-privacy-audit`, also for small fixes:

1. Check `README.md` and the files in `docs/` against the change and
   update them in the same commit.
2. Write the commit message as a Conventional Commit (`feat:`, `fix:`,
   `docs:`, ... see the `pre-commit-checklist` skill). `CHANGELOG.md` and
   the version files are generated by semantic-release; never edit them.
3. Check dependencies and toolchain for updates and *suggest* available
   updates (do not update on your own).
4. Check the licenses of third-party code and keep the license lists
   (`THIRD-PARTY-LICENSES.md`, `/licenses`) complete and current.
5. Run the `security-privacy-audit` skill on the staged changes and the
   commit message; do not commit while a check is `BLOCKED`.

Report the result of each step in one line in your answer and end with
the audit summary of `security-privacy-audit`.

## Invariants that must not break

- Every admin page, layout and **every server action** calls
  `requireAdmin(level)` itself; the panel layout alone does not protect a
  server action. Level 100-only entities keep `minLevel: 100`.
- SQL only through `src/lib/db.ts` with `?` placeholders. Identifiers in
  template strings only from constants or allowlists (`rankingSorts`,
  entity definitions), never from `searchParams`, `params` or form data.
- Admin writes use the admin DB user (`DB_ADMIN_USER`); public pages run
  with the SELECT-only `gamewe_web` user. Code for public pages must not
  call `adminQuery`/`adminExec`, except reading data the public may see.
- Public pages never show: hidden players (`hideranking`/`player_hidden`),
  IP addresses, RCON data, admin users, TOTP rows, chat unless the setting
  allows it.
- Secrets (`ADMIN_SECRET`, DB passwords) only from the environment
  (`src/lib/env.ts`), never in `NEXT_PUBLIC_*`, client components, logs,
  error messages or redirects.
- Cookies: `httpOnly`, `sameSite: strict`, `secure` behind HTTPS. The
  session cookie `gamewe_session` is scoped to the base path (admins see
  IPs and chat on player pages); the TOTP step cookie
  `gamewe_2fa` (5 min) to `${basePath}/admin`.
- Client IP for rate limits and logs: behind nginx the first
  `X-Forwarded-For` entry is client-controlled when nginx uses
  `$proxy_add_x_forwarded_for`; use a header nginx overwrites
  (`X-Real-IP`) or the last proxy-added entry.
- `.env`, `.env.local` stay ignored; examples use `change-me`.
